Add the interactive TUI (grfdoctor fix)

Implements the requested layout end-to-end, using tview:
  - Left: every referenced NewGRF, broken ones first (marked with a red
    !), ticked green once matched to a replacement or fully removed
  - Top-centre: detail of the selected GRF (slots, affected vehicle
    count, match status)
  - Bottom-centre: the affected vehicle list + per-vehicle detail
    (cargo, tile, and the actual railtype built under it -- Enter
    toggles carriage removal instead of replacement)
  - Right: a live-searchable browser of the full BaNaNaS NewGRF catalog
    (loaded via internal/bananas in the background on startup), with a
    download action that queues the extracted .grf for insertion

Matching prompts for the replacement engine's internal GRF-local ID
(this tool does not parse third-party GRF binaries to enumerate their
own engines -- documented limitation, see README.md) and shows
non-blocking date/railtype warnings (internal/engine/warnings.go) --
never blocking, per the explicit "user can do what they want" design.

'A' builds an engine.Plan from every item's match/removal state,
applies it, lints the result, and writes a NEW file (never touches the
original) -- aborting the write if linting finds a problem.

Verified both by a data-level test (internal/ui/model_test.go, asserting
broken-first ordering, correct railtype lookup, etc. against the real
fixture) and by actually running the compiled binary in a pty against
the fixture savegame -- confirmed correct rendering of all four panels
with real data (e.g. "Track here: Monorail" correctly shown for the
known-monorail vehicles) and no crash.

Scenery/object-GRF support is stubbed (ItemKind/KindObjectGRF exist,
but engine.Analyze only detects vehicle-referencing GRFs today) per the
explicit ask to make reasonable forward-looking assumptions without a
test case to verify against.
